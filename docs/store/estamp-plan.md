## 1. 方針と今回の公開範囲

**Tauri v2 化 → 設定・日付・画像生成の正常化 → 書体と UI の仕上げ → MSIX の確定 → 品質確認 → Store 提出**の順に進める。MSIX の試作だけは v2 化直後に前倒しし、配布方式の問題を早く見つける。

- estamp 本体は MIT、Store 価格は無料、初回は広告・アプリ内課金・試用期限を設けない。和暦と日付手入力も無料の基本機能に含める。
- 初回の最低範囲は、上段・下段の編集と保存、単一印影、正常な今日の日付、西暦／和暦、日付指定と今日に戻す、文字サイズ・出力サイズの調整、透過画像コピー、オフライン動作、日本語の操作・エラー表示。
- 複数プロファイル、色・枠線変更、独立した PNG ファイル保存は初回公開条件から外す。コピーした PNG は必須とし、ファイル保存機能とは分ける。企画部評価の機能充実項目をすべて初回に入れる案ではない。
- 当面の提出対象は **Windows 11／x64／日本語**を推奨。最低 OS ビルドは採用する Tauri v2・WebView2 と実機確認後に確定し、manifest と掲載文を一致させる。Windows 10、ARM64、英語、S モードの対応表明は別途判断する。
- MSIX のビルド工程は初回公開に含め、PLC タグ・モニタと ChronoGazer に渡せる形にする。Store ライセンスの Rust 共通部品は、無料公開後に実施する後続必須作業とする。無料公開をその完成待ちにしない。

### 設定保存とポータブル版の扱い

標準の論理保存先は **`%APPDATA%\<確定した Tauri identifier>\Setting.json`** とする。Rust の `app.path().app_config_dir()` で取得し、環境変数・ユーザー名の直書きや CWD への依存を避ける。Tauri のアプリ設定ディレクトリは identifier を使って分離される。[Tauri path API](https://v2.tauri.app/reference/javascript/api/namespacepath/)

MSIX ではパッケージ内への書込みは禁止される。また AppData は OS・manifest の仮想化設定に応じてパッケージ専用領域へ転送される場合がある。上記はアプリが扱う論理パスであり、エクスプローラー上の実体パスや Store 外版との設定共有を保証しない。PR-07・08 で実際の保存場所、更新保持、削除・再インストール時の挙動を記録する。仮想化を無効化する追加権限は初回に要求しない。[Microsoft: packaged desktop apps の実行とファイル操作](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes)

ポータブル版を初回に作り直さない理由は、MSIX では隣接設定ファイルを使えず、保存方式・更新・WebView2・テストが二系統になるためである。小規模な日付印アプリでは、無料公開と再利用基盤の確立を先にする方が費用対効果がよい。PR-00 の基準には CWD 相対の保存機能があるが、これだけで完全なポータブル性や MSIX での旧設定互換を検証済みとは扱わない。

将来残す場合は、同じコードから **Store 外向けの明示的な portable ビルド**を作り、`current_exe()` の親を基点とする。CWD や「隣に JSON があれば自動切替」には依存しない。書込み不可を表示し、Store ビルドではこの経路を無効化する。WebView2 のユーザーデータ等も含めて「PC に設定を残さない」という持ち運び要件を検証する必要がある。設定だけ隣接保存しても完全なポータブル性は保証できない。追加費用は概算 **1〜2 人日＋必要な WebView2 配布検証**で、今回の合計には含めない。

- schema version は **1**。既存 JSON の欠損項目には既定値を補い、型が不正な項目はエラーにする。`stamp_type` は `#[serde(default)]`、既定値は現在の三段日付印を表す `dated_stamp`（Rust: `StampType::DatedStamp`）。未知の印影種類は元の文字列を保持し、表示には既存の日付印を使う。未知の追加フィールドも JSON 値のまま保持する（方式 (2)）。この PR に印影種類の切替・UI・追加描画を含めない。日付3項目は PR-04 と共通の保存契約とし、読込・旧設定取込の共通経路で手動日付を検証・復元する。

- 同じフォルダーに一時ファイルを排他的に作成し、全量書込み・`sync_all()`・クローズ後に `std::fs::rename` で置換。Windows の一時的なアクセス拒否・共有違反・ロック違反は20ms間隔・最大300msを目安に再試行する。失敗は日本語で表示し、一時ファイルを削除する。Windows の既存ファイル置換は Rust テストを既存 Windows CI で実行する。Mac の成功だけで Windows 実機確認済みとは扱わない。
- UTF-8 BOM は解析時だけ除去し、revision には原文を使う。壊れた JSON／形式不正／不正 UTF-8 は同じフォルダーの `Setting.<識別子>.corrupt.json` に原文のまま退避し、保存場所を案内して既定値を使う。退避失敗・通常の読込失敗時は編集・保存を停止。不明な schema version は退避・上書きせず停止する。
- `Setting.lock` の OS ファイルロックで読込・退避・競合確認・保存を直列化する。ロックファイルは削除せず、ハンドル解放でロック解除。別ウィンドウが保存した場合は読込時の内容を表す `revision` と比較して後発保存を拒否し、再読込を案内する。ロック競合は20ms間隔・最大300msを目安に待ち、それでも取得できなければ再試行を案内する。対象はこの保存契約を使うアプリ同士で、外部エディターによる同時書込みまではロックできない。
- 「旧設定を取り込む」は **現在の実行ファイルと同じフォルダー**の `Setting.json` が存在するときだけ表示する（`legacy_available` コマンド）。保存後も取り込めるが、保存済み・編集中の値を置き換える確認を経て、revision が一致する場合だけ保存する。CWD や開発用の `src-tauri/Setting.json` を自動参照せず、旧ファイルは削除・変更しない。別の場所にある旧設定は利用者が実行ファイル隣へコピーしてから再読込する。テストはテスト内の旧6項目データを使い、追跡中の設定ファイルに依存しない。起動ウィンドウの寸法は変更せず、スクロールで設定・復旧操作に到達できるようにする。

詳細な IPC 契約・互換性の根拠・PR-04 との統合仕様は [設定ストアの仕様](../settings-storage.md) を参照。

発行元表示名 **Banto Works（確定）**、Tauri identifier、MSIX Identity Name、Identity Publisher（例: Store 割当の `CN=...`）、Store ID、PFN はそれぞれ別の値として管理する。Publisher に表示名を推測で入れない。[Microsoft: Product identity](https://learn.microsoft.com/en-us/windows/apps/publish/view-app-identity-details)

通常の Tauri Win32 プロセスを full trust で包装するなら、manifest の **`runFullTrust` は restricted capability** として扱い、必要理由を提出情報へ書く。これは管理者昇格とは別である。評価資料の「restricted capability も不要」は、この MSIX 構成では修正する。[Microsoft: desktop MSIX manifest](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-manual-conversion)

版は単一の入力から Cargo／Tauri／package／MSIX に反映する。初回は例としてアプリ `1.0.0`、MSIX `1.0.0.0`。提出の再ビルドは単調増加させ、Store 向け第4桁は 0 にする方針とする。[Microsoft: パッケージ要件・版番号](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/package-version-numbering)

- **受け入れ条件:** package identity なし、Store 未取得、API エラー、オフラインを「未購入」と同じ bool に潰さない。`Available(snapshot)`／`Unavailable(reason)` 等で取得結果と権利状態を分ける。未知・期限切れ時にどの機能を許すかは各有料製品のポリシーとし、共通 crate に決め打ちしない。estamp では失敗しても全基本機能が使え、ライセンス照会は明示的な開発・診断経路に限定する。通常起動で新しい Store 通信を必須にしない。
- **引渡し条件:** crate の版・MIT・Windows SDK／windows crate の採用条件・Tauri adapter 例・製品別設定例を揃える。後続製品が使う所在地（共通リポジトリ等）を決め、固定した版／コミットで依存できるようにする。ローカル絶対パス依存やソースの手コピーを完成形にしない。

デスクトップの StoreContext は親ウィンドウの関連付けが必要で、購入 UI などの誤動作を避けるため `IInitializeWithWindow` を適切に使う。Store の実ライセンス試験には、対応するアプリを Store で公開して端末へ取得する準備が必要であり、単に自己署名 MSIX を入れただけで完了しない。[Microsoft: Store API・デスクトップ・試験手順](https://learn.microsoft.com/en-us/windows/uwp/monetize/in-app-purchases-and-trials)

### PR-R2：Store 実機試験・失敗系・後続製品への利用契約（1〜2 人日）

- **目的:** MSIX と共通 crate を、他製品で利用できる根拠付きで引き渡す。
- **変更範囲:** Store 配布版 estamp の診断試験、模擬 backend を使う単体試験、診断結果・再現手順・利用者向けではない開発資料。必要なら公開後の estamp 更新版を用意する。
- **依存関係:** PR-09・R1、Store からの取得と一度の起動。品質・リリース部の試験用端末・アカウント。
- **担当:** 開発・品質・セキュリティ・リリース。
- **受け入れ条件:** 無料本体の有効ライセンス、identity なし、照会エラー、オフライン／キャッシュ、再照会を確認。返された値とアプリ側判断を分けて記録。模擬試験は試用中・期限切れ・未購入・購入済みを網羅するが、Store の本番課金試験の代わりとは扱わない。PLC タグ・モニタ／ChronoGazer の担当に、crate の固定版、製品設定例、状態一覧、試験一覧、未検証項目を渡す。両製品のコード自体は本計画の対象外。

`GetAppLicenseAsync` はオフライン時に端末のキャッシュを返す仕様があるため、常にオンラインの最新状態とみなさない。[Microsoft: GetAppLicenseAsync](https://learn.microsoft.com/en-us/uwp/api/windows.services.store.storecontext.getapplicenseasync)

**再利用できるもの:** MSIX の収集・パッケージ化・署名分離・版検証・試験手順、ライセンス取得の仕組み、型、エラー処理、HWND adapter。**製品ごとに必要なもの:** Store identity／価格／アドオン ID、制限する機能、試用終了時・オフライン時の動作、掲載・プライバシー文、実課金の試験。

無料 estamp の本体だけでは有料本体の試用・購入完了までは検証できない。これらは PLC タグ・モニタ等の有料製品の限定公開で検証する。限定公開でも審査・公開・Store 取得の準備を見込む。初回 estamp に評価資料の有料アドオンを足す案は採らない。購入 API まで先行共通化するなら **別 PR で 1〜2 人日以上**を追加し、取消・既購入・失敗・再取得・購入後再照会を含める。返金やプロモーションコードを使えると仮定した日程にはしない。[Microsoft: 価格・試用設定](https://learn.microsoft.com/en-us/windows/apps/publish/publish-your-app/msix/price-and-availability)

企画部の **8〜13 人日**は基準として尊重する。ただし指定 HEAD では保存・編集等が未実装であり、初回機能を絞っても **9〜14 人日**を現在の作業予算案とする。評価対象と同じ進んだソースが見つかれば、重複実装を除いて 8〜13 人日へ近づけられる可能性がある。根拠なく同じ見積もりに据え置かない。

この合計は開発だけでなく各 PR に書いたデザイン・品質・企画・リリースの小規模な協働分を含む概算であり、他部門の同じ作業をもう一度加算しない。専任デザインの大幅な作り直し、多数の審査差戻し、Windows 環境の新規調達、独自 CI 基盤構築、WebView2 固定版同梱対応は含めない。これらが必要なら別に再見積もりする。

実働の初回公開準備は、おおむね開発主担当 1 名で約 2〜3 週間に、他部門の並行作業を組み合わせる想定。アカウント確認・名前予約・審査・公開反映の待ち時間は人日と別で、公開日を確約する数値ではない。ライセンスの実機検証は Store 取得可能になるまで待つ必要がある。

## 8. 主なリスクと対処

| リスク | 影響・早期に見る兆候 | 対処・担当 |
| --- | --- | --- |
| 評価資料とソースの相違 | 8〜13 人日から超過、旧設定互換の作り直し | PR-00 で対象を確定。別版を確認できない場合は本計画の 9〜14 人日を採用／開発・企画 |

| WebView2・MSIX 構成 | 手元では動くがクリーン端末で起動しない、サイズ増大 | PR-07 試作を前倒し。ランタイムなし環境と通常ユーザーで導入確認。固定版採用なら追加費用を判断／開発・品質 |

公開判定は「基本機能が動く」「設定が保持される」「オフラインで同じ印影になる」「権利表示・権限・CSP が確認済み」「同一候補の品質報告と WACK 記録がある」「掲載内容が実物と一致」のすべてを満たした時点とする。
